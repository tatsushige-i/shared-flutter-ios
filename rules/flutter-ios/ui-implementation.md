# UI Implementation Rules

Flutter の UI 実装で踏みやすい落とし穴をまとめる。`lib/features/**/presentation/` の
ウィジェット実装はすべて本ルールに従うこと。

## テキスト入力とウィジェット再構築

### ルール

フォーカス中の `TextField` を含むサブツリーを貼り替える前に、必ずフォーカスを外す。

```dart
FocusManager.instance.primaryFocus?.unfocus();
```

貼り替えの例:

- レコード削除後の再読込
- 日付・対象の切り替えによるフォーム貼り替え
- リスト項目の削除・並び替え

### 理由

フォーカス中の `TextField` は生きた `TextInputConnection` を持っている。そのサブツリーが
再構築され、旧 `EditableText` が破棄されて新しい `EditableText` が同じ接続を引き継ぐと、
エンジン側が保持している「編集中の値」が新しいクライアントへ書き戻される。空で初期化した
はずの `TextEditingController` に、削除したはずの古い値が残る。

### 二次被害

書き戻しは通常の入力と区別なく `onChanged` として届く。自動保存（debounce 保存など）と
組み合わさっていると、この書き戻しがそのまま保存されてしまい、**削除したはずのレコードが
復活する**経路になる。単なる表示の乱れではなく、データ破損につながる。

### 検証上の注意（重要）

**ウィジェットテストでは再現しない。** `flutter_test` の `TestTextInput` はテスト用の
フェイクであり、実機／シミュレータのエンジンが行う値の push back を再現しない。そのため
このバグを再現するテストを書いても、CI 上は緑のまま通過する。

- ユニットテスト・ウィジェットテストの green は、この種の不具合の不在を保証しない
- フォーカス中の `TextField` を含む画面でサブツリーの貼り替えを伴う変更を行った場合、
  実機またはシミュレータでの目視確認を必須とする
- 特に「フォーカスを当てた状態で削除・切り替え操作を行う」手順は明示的に確認する

### 適用が必要になりやすい箇所

- 入力欄が動的に増減するフォーム（自動保存対応の画面など）
- 削除操作の直後に同じ画面を再読込するフロー
- 日付や対象切り替えでフォーム全体を作り直す画面
